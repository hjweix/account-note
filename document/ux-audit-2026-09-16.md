# Account Note 交互体验全面评估（2026-09-16）

评估范围：content 弹窗（页面内备注弹窗 + 拾取模式）、工具栏 Popup、管理页三端。
评估依据：src/content.js / src/popup.js / src/management.js / 三份 CSS / HTML 结构逐行走读。
严重度定义：P0 = 核心流程受阻、误导用户或数据风险；P1 = 明显摩擦、效率损失；P2 = 打磨项。

---

## 一、P0 问题（按影响排序）

### P0-1 管理页「标签管理」是假功能，误导用户

**位置**：`management.js` `addNewTag()`（L1796-1819）

**现状**：设置页「标签管理」卡片提供输入框 +「添加」按钮，点击后 toast 提示「标签添加成功」，但代码注释自己承认：*「标签只是存储在备注中的字符串，所以我们只需提示添加成功，实际创建标签需要在编辑备注时添加」*——**什么都没有创建**。新标签不会出现在筛选器里（筛选器只统计已被备注使用的标签），用户按提示去用却找不到，属于功能性谎言。

**建议**：
- 方案 A（推荐）：去掉独立输入框，标签管理卡片只展示「已被使用的标签 + 使用计数」，把「添加」动作收回备注侧（弹窗的 + 标签）。入口与数据同源，无谎言。
- 方案 B：真实现——在 storage 加 `customTags` 键，筛选器合并 `getAllTags()` 与自定义标签，标签管理可增删改。
- 无论哪个方案，`addNewTag` 的成功 toast 必须删掉。

**收益**：消除「操作成功但结果不存在」的信任损耗；标签体系入口与数据一致。

### P0-2 Popup「添加备注」入口自相矛盾，两条路都走不通

**位置**：`content.js` onMessage `showAddNotePopup`（L1475-1481）、`content.js` clickHandler（L1271-1282）、`popup.js` showEmptyState

**现状**：空状态下 popup 显示「添加备注」按钮，点击后 content 侧执行：
1. 页面**没有密码框** → `if (passwordField)` 直接跳过，**无任何反馈**，用户点了像没点；
2. 页面**有密码框** → 弹窗挂在密码框旁，但用户账号框是空的，点正文立即 toast「用户名不能为空」——用户被引导到一条走不通的路上。

矛盾根源：备注 key = `origin_用户名`，没有用户名就没有归属，但界面没有把这个前提讲清楚。

**建议**：
- content 侧找不到密码框时回传 `{ ok: false, reason: 'no-password-field' }`，popup 按 reason 提示「本页未找到登录表单，请先聚焦账号输入框」；
- 弹窗空账号态的正文文案从「添加备注」改为引导式文案（i18n 新 key，如「先在下方输入账号，即可为它添加备注」），点击时不再报错式提示，而是聚焦宿主页账号框（`field.focus()`）；
- popup 空状态的按钮文案同步改为「去页面添加」，并在 content 不可达（`try/catch` sendMessage 失败）时提示「请刷新页面后重试」（当前 `showAddNotePopup` 消息失败完全静默）。

**收益**：把「首条备注怎么建」这条最关键的新手路径从死胡同变成引导流。

### P0-3 弹窗关闭按钮 ✕ 实际是「禁用菜单」，语义错位且不可达

**位置**：`content.js` closeBtn 事件（L1304-1322）、`showDisableOptions()`（L263 起）

**现状**：头部 ✕ 按钮，用户预期是「关闭弹窗」。实际行为：
- **hover**（不是点击）才展开禁用菜单，点击无反应；
- 弹窗的真正关闭方式是「点击弹窗外部」，没有任何视觉提示；
- 禁用菜单只有 hover 触发，键盘用户、触屏用户完全无法使用禁用功能；
- 「在所有网站上禁用」这种高影响操作无任何确认，一步生效。

**建议**：
- ✕ 改为点击关闭弹窗（调用 `destroySuggestion`），符合所有平台的通用约定；
- 禁用菜单改为点击齿轮/⋮ 图标打开（新增第四个头部按钮，或长按 ✕），保留 hover 作为加速方式；
- 菜单里「在所有网站上禁用」项加警示配色（danger 红），点击后 toast 文案附带回退路径提示（「可在扩展弹窗一键重新启用」——popup 已有 enableCurrentSite 通道，文案如实）。

**收益**：修复语义错位；禁用功能对键盘/触屏可达；误触全局禁用的概率下降。

### P0-4 删除操作：原生 confirm + 无撤销，数据风险感知差

**位置**：`management.js` `confirmDelete()`（L1320-1325）、deleteNotes、deleteTag、`clearAllDataBtn`（L1626-1634）

**现状**：
- 所有删除确认用原生 `confirm()`，与三端原生化的视觉语言完全断裂；
- 删除备注/批量删除/清空全部数据**都没有撤销**。清空数据文案说了「无法恢复」，但用户手滑点掉的**单条**备注同样无法恢复；
- 批量删除成功后 toast 文案错误复用了 `importSuccess`（「成功导入 N 条」），删除说成导入，误导。

**建议**：
- 短期：批量删除的 toast 换用正确的 i18n key（新增 `deletedCount`）；单条删除维持 confirm 但文案写明目标（「删除 github.com / alice 的备注？」——现在只问「确定删除吗」不说是哪条）；
- 中期：confirm 换成自绘确认对话框（三端已有 design token，成本低）；
- 关键改进：**软删除**——删除先移入 storage 的 `trash` 键（保留 7 天），toast 给「撤销」按钮，7 天后启动时清理。这是备注类工具的行业标准做法，成本可控。

**收益**：误删可救回；确认文案具体化让用户知道删的是什么；toast 不再说谎。

## 二、P1 问题（按影响排序）

### P1-1 favicon 走 google.com 服务，国内环境全部破图

**位置**：`management.js` displayNotes L363、loadDisabledSites L658

`https://www.google.com/s2/favicons?...` 在国内网络不可达，管理页所有域名图标显示为破图/空白，且每次渲染都发起必然失败的请求。**建议**：多级降级——先试 `https://favicon.im/{host}` 或 `https://api.iow.cn/favicon/{host}` 等国内可达源，加载失败 `onerror` 时回退到现有的首字母头像（popup 已有同款组件，直接复用样式）。**收益**：管理页视觉完整度恢复，消除无效网络请求。

### P1-2 长备注只读态无法查看全文

**位置**：`styles.css` `.note-text-readonly`（line-clamp: 3）、M1 删除了展开/收起按钮

M1 砍掉按钮是正确方向，但**只读查看全文**这个需求被一并砍掉了：超过 3 行的备注，只读态永远看不全，唯一看全文的方式是进入编辑态（还会意外触发保存语义）。**建议**：正文 line-clamp 末尾加「…更多」链接（CSS 无法检测截断，JS 用 `scrollHeight > clientHeight` 判断后追加），点击原地展开/收起，不动按钮结构。**收益**：恢复长备注可读性，且不增加常驻按钮。

### P1-3 无备注记录上的操作静默失败

**位置**：`content.js` 标签添加（L1358-1360）、收藏按钮 disabled 无解释

- 记录尚无备注时点「+ 标签」：`currentData` 不存在直接 `return`，无提示；
- 收藏按钮 disabled 但没有 title 解释为什么不能点。

**建议**：两个入口统一提示「请先保存备注内容」（新增 i18n key）。收藏按钮 disabled 时给 `title="先填写备注后可收藏"`。**收益**：消除「点了没反应」的困惑。

### P1-4 反馈机制弱：toast 无类型区分、停留短、噪音不均

- popup / management 的 toast 无 success/error 视觉区分（content 端有 ✓/⚠️ 图标，另外两端没有）——不一致；
- 错误提示同样 2 秒消失，用户来不及读；
- 收藏这种高频微操作每次都弹 toast（popup L307、management L1062），提示噪音大于价值。

**建议**：toast 组件三端统一（实心表面 + 左侧 3px 状态色条：成功绿/错误红/中性灰）；error 类型停留 4s；收藏操作去掉 toast，状态本身就由星标颜色即时反馈。**收益**：反馈信号的信噪比提升，错误信息真正被读到。

### P1-5 生产代码残留大量调试日志，且打印敏感数据

**位置**：`management.js` 全文 40+ 处 `console.log`，其中 L247-248 打印全部存储 key、L1020-1026 打印完整备注数据到控制台；`content.js` `getFieldKey` L538 每次生成 key 都打印用户名。

**建议**：webpack TerserPlugin 生产构建已剔除 console，但需确认 drop_console 配置覆盖 management（当前 build 是生产模式，若已生效则风险仅在 dev——**应实测验证 dist/management.js 无日志**）；同时把 `getFieldKey` 的日志降为 `DEBUG` 开关控制。**收益**：用户名不落控制台；性能无损。

### P1-6 管理页首屏无加载状态

**位置**：`management.js` loadAllNotes（先 await 迁移再读取再渲染）

首屏渲染前 `notesList` 是空白 div，数据量大时用户看到一段白屏，无法区分「没数据」和「在加载」。**建议**：渲染前先插入 4-6 张骨架卡片（CSS 渐变动画即可），`displayNotes` 时替换。**收益**：感知性能提升，消除「闪空状态」错觉（空状态 flash 会让用户误以为数据丢了）。

## 四、做得好的部分（保持现状）

- **拾取失败分流提示 + 一键启用**（871a22e）：禁用类失败给恢复入口而非「请刷新」，是本轮已修复的最佳实践；
- **弹窗定位实测宽高 + 右侧避让密码管理器**：尊重浏览器原生 UI 的辅助定位原则正确；
- **行内编辑统一交互语言**：弹窗点击正文编辑、popup 点击行编辑、Enter/Esc 语义三端一致；
- **备份信封 v2 的通用切分规则**：新增 key 自动进备份，向后兼容旧格式；
- **空状态/无结果状态有区分**（管理页搜索无结果 vs 真空状态文案不同）。

## 五、优先级汇总表

| 优先级 | 问题 | 改进方向 | 预估成本 | 预期收益 |
|--------|------|----------|----------|----------|
| **P0-1** | 标签管理假功能 | 入口收回备注侧，删虚假 toast | 小 | 消除误导 |
| **P0-2** | 添加备注流程走不通 | 结构化回传 + 引导文案 + 聚焦账号框 | 中 | 首条备注路径打通 |
| **P0-3** | ✕ 按钮语义错位、禁用菜单不可达 | ✕ 恢复关闭；禁用入口改点击式 | 中 | 修复核心语义 + 可达性 |
| **P0-4** | 删除无撤销 + confirm 风格断裂 + 文案错误 | 软删除 + 撤销 + 自绘确认 + 修 toast key | 大 | 数据安全网 |
| **P1-1** | favicon 破图 | 换国内可达源 + 首字母兜底 | 小 | 视觉完整 |
| **P1-2** | 长备注看不全 | 截断处加「更多」原地展开 | 小 | 可读性 |
| **P1-3** | 静默失败 | 统一提示「先保存备注」 | 小 | 消除困惑 |
| **P1-4** | toast 无类型/噪音不均 | 三端统一组件 + error 停 4s + 收藏去 toast | 中 | 反馈质量 |
| **P1-5** | console 泄漏敏感数据 | 验证 drop_console + DEBUG 开关 | 小 | 隐私 |
| **P1-6** | 首屏无加载态 | 骨架屏 | 小 | 感知性能 |
| **P2-1~8** | 8 项打磨 | 见上表 | 各小 | 细节一致性 |

**建议实施节奏**：P0-1 / P0-2 / P0-3 + P1-1 / P1-2 / P1-3 / P1-5 合并为一个「交互修复」迭代（多数是小改动）；P0-4 软删除与 P1-4 toast 组件统一作为下一个独立迭代；P2 随手修。
